# Glint M13 Candidate Context Validation

- 日期：2026-10-21
- 分支：`fix/candidate-context-validation`
- 目标：修复蓝色消息胶囊误选、长焦点候选识别失败和 HUD 上下间距观感不一致

## 结论

保留稳定的“系统强调色焦点胶囊 + 单候选 OCR”主链路，不恢复整条候选栏
OCR。只有在截图出现多个蓝色区域，或焦点候选宽度超过常规比例时，才用
候选行中的连续序号做一次轻量上下文校验。

## 已确认原因

1. 旧实现按距光标远近选择蓝色连通区域。微信、飞书等界面中的蓝色消息
   胶囊可能距离更近，导致 HUD 定位到错误区域。
2. 旧实现固定拒绝宽高比超过 `6:1` 的蓝色区域，长句候选会被直接丢弃。
3. 只在候选横带内运行 Vision Fast 会漏掉部分飞书候选行；长候选行则
   需要 Vision Accurate 中文识别才能稳定提取序号。
4. HUD 的上下定位公式本身对称：
   - 上方：候选区域顶部 + 间距
   - 下方：候选区域底部 - HUD 高度 - 间距

   实际间距不一致主要来自选错候选区域，而不是上下公式不同。

## 实现边界

- 单蓝色区域且宽高比不超过 `6:1` 时保持原快路径，不增加 OCR。
- 蓝色区域宽高比最多放宽到 `18:1`，用于长句候选。
- 多个蓝色区域时，只接受与候选行连续序号重叠的区域。
- 单个长候选同样要求候选行序号证据。
- 存在歧义但找不到连续序号时静默隐藏，不按距离猜测。
- 序号识别先尝试 Vision Fast 的全截图、候选横带和紧凑横带；全部失败
  后才回退 Vision Accurate 中文识别。
- 每个识别区域按顺序执行，得到有效行后立即结束，不继续运行其余 OCR。
- 单长候选直接使用 Accurate 竖带校验，跳过无效的 Fast 轮次。
- 同一蓝色区域的垂直几何在 500ms 内复用校验结果，避免连续轮询重复 OCR。
- 候选文本仍只 OCR 最终选中的焦点胶囊。
- HUD 上下定位统一由纯几何布局计算，上方和下方使用同一间距。
- HUD 关闭 `NSPanel` 外部阴影，避免阴影侵入上下间距造成视觉不对称。
- 不读取输入框正文，不保存截图、候选文本或序号识别结果。

新增覆盖：

- 蓝色消息比真实候选更靠近光标时，仍选择候选区域并识别出“你好”。
- 多个蓝色区域且没有有效序号行时返回空结果。
- 合并、粘连的 OCR 文本仍可提取连续序号。
- 分离序号必须满足共同基线、合理间距和连续顺序。
- 长候选可进入上下文候选集合，但没有序号证据时拒绝。
- 内置候选样本可以识别出与其垂直重叠的候选行序号。
- 真实长候选截图经 Accurate 回退选中焦点胶囊，并识别出
  “今天天气不错哈哈哈”。
- 飞书截图包含头像和蓝色消息时，经 Fast 全截图回退正确选中“你好”。
- HUD 上方和下方布局在相同 `7pt` 设置下保持完全一致的几何间距。
- 同机 Release 微基准中，长候选首次校验由约 185ms 降至约 80ms；
  相同几何的后续轮询命中缓存，只保留焦点 OCR 成本。

真实微信、飞书和长句候选仍需人工验收；自动化测试不替代系统输入法和
第三方 App 的实机行为。
